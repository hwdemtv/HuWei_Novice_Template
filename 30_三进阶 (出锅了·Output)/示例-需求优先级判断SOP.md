# 📋 需求优先级判断 SOP

> 本 SOP 用于解决需求评审中的优先级争议。
> 当产品和技术对优先级有分歧时，用此流程做决策。

---

## 🎯 适用场景

- 需求评审中出现优先级分歧
- 季度规划时需要排列需求顺序
- 临时插入需求时判断是否应该插队

---

## 📋 判断流程

### Step 1｜列出待评估的需求

把争议中的需求都列出来，每个需求填写以下信息：

| 需求名称 | 来源 | 预估工期 |
|---------|------|---------|
| | | |

### Step 2｜四维评分

对每个需求，按以下四个维度打分（1-5 分）：

| 维度 | 权重 | 评估问题 | 需求 A | 需求 B |
|------|------|---------|--------|--------|
| 用户影响 | 30% | 影响多少用户？问题严重程度？ | | |
| 系统风险 | 30% | 不做会导致什么技术后果？ | | |
| 战略对齐 | 20% | 和本季度 OKR 的关系？ | | |
| 实施成本 | 20% | 需要多少人/天？（越少分越高） | | |
| **加权总分** | | | | |

### Step 3｜决策规则

1. **总分高者优先**
2. **总分相同时**：系统风险维度高者优先（技术债利滚利）
3. **仍无法决策时**：升级到部门负责人，但必须带着评分表

### Step 4｜记录决策

在需求管理系统中记录：评分结果 + 最终决策 + 决策人

---

## ⚡ 快速检查清单

- [ ] 所有争议需求都已评分
- [ ] 评分时参考了数据（用户反馈数 / 系统监控指标）
- [ ] 决策已通知所有相关方
- [ ] 决策已记录在案（可追溯）

---

## 📌 注意事项

1. **评分要基于数据，不是感觉**。用户影响看反馈数量和严重程度，系统风险看监控指标和技术评估。
2. **紧急 ≠ 重要**。紧急需求可以插队，但必须说明原因，并在下次评审时复盘插队是否合理。
3. **定期回顾**。每季度回顾一次 SOP 的使用情况，根据实际效果调整权重。
